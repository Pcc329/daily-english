📖 今日文法重點 — 因果句型 Cause & Result
技術報告、Slack 更新、PR 描述最常用因果句型，說明「為什麼做」和「結果怎樣」。

✅ 原因（because / since）：The cutover was safe because a rollback switch was in place.
✅ 結果（therefore / as a result）：All six tests passed; therefore the cutover proceeded.
✅ 原因（due to）：Users noticed nothing due to the seamless design.
✅ 結果（as a result of）：As a result of the feature flag, rollback takes only seconds.

口訣：because / since / due to 後面說原因；therefore / as a result / consequently 後面說結果。

朗讀練習
段落一 — 今天發生了什麼？
💡 底線單字可點擊單獨發音

Today we completed the production cutover.
The data source for three APIs was switched from Airtable to Supabase.
Because all six acceptance criteria had passed, we decided to proceed.
As a result, the system is now running on Supabase in production.

段落二 — 誰動了，誰沒動？
💡 底線單字可點擊單獨發音

The frontend was not moved. Since it stayed in place, users noticed no difference.
The API layer was updated to read from Supabase instead of Airtable.
The AI feature was also unchanged, because it calls the Claude API directly and does not depend on the database.
Due to this design, the migration was completely seamless.

段落三 — 六項驗收全過
💡 底線單字可點擊單獨發音

Six acceptance criteria were checked before the cutover.
The record count was 2,463 — consistent with the pre-cutover baseline.
The API returned real tax IDs, which confirmed that data was being read from Supabase.
The 26 retired records were excluded correctly.
As a result of passing all six checks, we had full confidence to proceed.

段落四 — 兩個計數為什麼都對？
💡 底線單字可點擊單獨發音

There are two record counts in the system: 2,463 and 2,485.
Both are correct, because they use different counting rules.
The statistics API applies stricter filters; therefore it returns 2,463.
The list API returns the raw count of 2,485.
Since the difference comes from status filtering, not data loss,
there is no discrepancy to fix.

段落五 — 為什麼可以放心？（主管問答）
💡 底線單字可點擊單獨發音

Can we roll back if something goes wrong?
Yes, we can. Because we used a feature flag, rollback takes only seconds.

Is Airtable still running?
Yes, it is kept as a backup for three months.

What happens if there is a problem?
We switch the flag back to Airtable.
As a result, there is zero risk of data loss.

The production cutover is complete.
Because all six acceptance criteria passed, we switched from Airtable to Supabase.
The migration was seamless — users noticed no difference.
As a result, we are now in a three-month observation period.

進階版：

今日總結

今天英文主題是用因果句型描述 Cutover 的決策邏輯。

中文你說的是：
「六項驗收全過，所以我們今天早上切換了。前端沒動、AI 沒動，只有 API 的資料來源換掉。因為用了 Feature Flag，就算出問題也能秒回滾。Airtable 再保留三個月當保險。」

Because all six acceptance criteria passed, we completed the production cutover this morning.
The frontend and AI remained unchanged — only the API data source was switched.
Due to the feature flag design, rollback takes only seconds if needed.
Therefore, Airtable is kept as a backup for three months.

因果句型是技術報告的骨架：先說原因（because / due to），再說結果（therefore / as a result）。這樣的英文報告讀起來邏輯清晰，主管一眼就懂。
